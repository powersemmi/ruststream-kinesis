# 基准测试

通过这个 crate 拿到一条 Kinesis 记录，每条都要花时间：分片读取、解码、结算。本页给出这份代价，对照
手写在 `aws-sdk-kinesis` 上的同样工作测得。

同一个进程里的三个循环跑同一个场景，彼此的差别在于由什么来搬运一条记录。**裸客户端**直接驱动
`aws-sdk-kinesis`：用 `PutRecord` 发布，用 `GetRecords` 读取。**本 crate** 驱动这个 crate 自己的类型 -
它的 Broker、它的订阅、订阅产出的流、它的确认和它的发布者 - 循环写在基准测试里，没有处理器，也没有运行时。
**整个服务**是用户会写的东西：应用对象之下的一个 `#[subscriber]` 处理器。

其余一切都相同：同一个 `SdkConfig` 构建每个客户端，流只有一个分片，三者用同样的 `GetRecords` 上限和
同样的空读暂停读它，解码成同一个类型，写同样的检查点，跑在同一个 tokio 运行时和同一次构建上。测量流程
是框架自己的，写在
[RustStream 基准测试页](https://powersemmi.github.io/ruststream/latest/benchmarks/#methodology)；本页
发布的是它在这里得出的结果。

!!! warning "这里回应的是模拟器"

    Kinesis 没有可以自己运行的服务端，所以三个循环都连到实时测试所用的 LocalStack 镜像。这个对照仍然
    成立，因为同一个模拟器回应三者 - 但它的饱和特征不是托管服务的：没有 TLS 握手，没有凭证刷新，没有
    区域延迟。这里的一行讲的是一条记录在这个 crate 里的代价，完全不讲一个服务在某个区域里的代价。

两列百分比回答两个不同的问题。`crate 相对客户端`是这个 crate 自己的消费端和发布者在它们所包装的客户端
之上的代价，这是本仓库要回答的问题。`服务相对客户端`是一个完整服务要付的代价；运行时加上去的那一份落在
两列之间，它发布在这里而不是随核心一起发布，因为它是关于这个 crate 与运行时如何衔接的事实：流怎样产出
记录、投递怎样到来、背压怎样传到消费端。

两个场景都读一个分片，每次 `GetRecords` 调用要 1000 条记录，空读之后暂停 20 毫秒，而每个循环每次调用只
发布一条记录，因为这个 crate 的发布者就是这样发布的。这些数字决定一个分片能交付多少，所以处处一致，读
这一行之前值得先知道它们。

两行的差别在于确认写到哪里。这个 crate 通过租约存储为分片写检查点来结算一条记录，而这个存储是可替换的：
默认的把检查点留在进程内，`DynamoDB` 的那个把第二个服务放进链路。裸循环把同样的检查点写到同样的地方 -
单元格里的一个字符串，或者对同一张表的同一个条件 `UpdateItem` - 所以分开两行的是存储，不是这个 crate。

标为 `indistinguishable` 的百分比，是它所比较的两列之差小于任何一列各次运行之间的离散度。低于运行间
噪声的数字，读起来像是从未测到的精度，所以不发布。

标为 `emulator-bound` 的一行，是一条投递所花的往返已经占了它时间的一半或更多。往返时间单独测量：对着
那套服务，在写入第一条记录之前测，并随下面的环境一起发布；一条投递摊到的往返，是它在一次 `GetRecords`
调用中的份额，加上在带检查点的那一行里结算它的那次条件写。带标记的一行是说，crate 和运行时的工作发生
在读取端本来就要付的等待里面：两列百分比因此不是代价的测量值，而是它的下界。

今天两行都没有带上这个标记。一次轮询最多带回一千条记录，所以它摊到一条投递上的份额很小；在带检查点的
那一行里，结算写是一次独立的往返，占那里一条投递代价的三分之一左右。给这些运行定节奏的是算式没有计入
的东西：模拟器能接受多少。无论由哪个循环发布，一个分片每秒只能向它写入几百条记录，所以三列都落在彼此
的离散度之内。这些行说明，这个 crate 和运行时都没有高出这条地板；它们没有说，在一台比它们更快的测试台
上三者会如何比较。

同一次运行的机器可读形式，框架站点用它构建跨 Broker 的汇总表，在
[`benchmarks/results.json`](https://powersemmi.github.io/ruststream-kinesis/latest/benchmarks/results.json)。

## crate 自身的代码

<div id="benchmark-code"></div>

第二张表是本 crate 自身在每条消息上的开销，是数出来的，不是计时得来的：指令数由 callgrind 统计，
内存分配次数由 DHAT 统计。每个场景都是用户会写的那种服务：`KinesisBroker` 按服务的写法构建，由运行时
启动，连的是同一套 LocalStack。服务用本 crate 的分片读取器通过 `GetRecords` 读取只有一个分片的流，
通过默认的租约存储结算，并用 `PutRecord` 回复。

计入的是服务线程执行的全部内容：框架的分发、本 crate 的代码，以及 AWS SDK 构建、签名和解析请求的工作。
模拟器是另一个进程，不计入。记录在计数开始之前从第二个线程发布，服务从为这次运行创建的流的最早保留记录
（`TRIM_HORIZON`）开始读取。

指令数和分配次数都是稳态下每条消息的值：1000 次投递的运行和 2000 次投递的运行之间的斜率。一次分片读取
由它返回的记录分摊，所以每一行都带着一次读取的份额：前两行一次读取最多返回一千条记录，第三行一次读取返回
一批。最后一列是启动服务并处理第一次投递一次性付出的开销：连接、打开订阅、列出分片、取得分片的租约和
迭代器。这些数字是绝对值，框架自身的开销也算在内；框架单独的开销由核心库在它的
[基准测试页面](https://powersemmi.github.io/ruststream/latest/benchmarks/)上公布。

同一次构建的多次运行之间，指令数的变化不到百分之零点五，最长的几次运行里分配次数会差几个块，因为服务做的是
真实的 I/O：一次运行结束时可能还有一次读取在途中，租约续期和分片同步也由定时器触发。每个下限都定在见到的
最大值之上。
`just bench-code` 在分配次数超过场景声明的下限时失败，加上 `--baseline=main` 时，指令数多出百分之二
以上也算失败；改变开销的合并请求要附上自己的数字。

## 机器

<div id="benchmark-environment"></div>

构建标志与数字一起发布，因为它们会改变数字：用 `-C target-cpu=native` 构建的二进制给出的数值，别的
机器无法复现，所以配方在构建前清掉这个变量。

## 它们不代表什么

这是一个分片、一个消费端、512 字节的消息体和回环上的模拟器。它测的是一条记录在这个 crate 里的代价，
不是 Kinesis 能承载多少；这里的一行与为另一个 Broker 发布的一行不可比：各种传输每条记录做的工作不同。

一次运行测量的窗口，从第一次投递开始，到最后一条记录的字段被读出为止，三个循环都一样，所以结算那条记录
的检查点在哪里都落在数字之外。

给流灌入记录的一端全速运行，绝不用来给消费端定节奏，所以追上它的消费端要付空读之后的暂停。这个暂停是
一次轮询，算在投递头上；它在一行里占多少，由上面的往返算式说明。

这些数字是一台机器在某一天的快照。
它们由人手工重测，测量期间机器只跑这一项：这一页要讲的差值，比与其他任务共用的机器上的噪声还小。

## 自己跑一遍

```bash
just bench
```

这个配方从 `docker-compose.test.yml` 启动那套服务，跑完两个场景，停掉它，并用测得的结果重写
`docs/benchmarks/results.json`。它要花几分钟，并且需要整台机器。每次运行都建立自己的单分片流，带
检查点的场景还建立自己的租约表，所以一次运行绝不会看到上一次留下的东西。记录条数不是固定的：一次探测
运行把它定下来，使每次被测运行在所在机器上至少持续五秒。

```bash
just bench-code
```

这个配方启动同一套服务，在 valgrind 下统计代码表，再把它停掉，并重写同一份文档里的 `code` 部分。它要
花几分钟；除了那套服务，还需要 valgrind 和基准测试运行器：
`cargo install --locked gungraun-runner --version =0.19.4`。
