# Kinesis {#kinesis}

`ruststream-kinesis` запускает сервис RustStream на Amazon Kinesis Data Streams. Kinesis - это
сегментированный лог с хранением записей. Подписка читает с любой позиции, которую поток ещё хранит,
и перематывается на ходу. Подтверждение - это контрольная точка отдельного сегмента, и в каждый
момент сегмент читает один экземпляр сервиса.

Над SDK крейт даёт то, что нужно потребителю лога: поиск сегментов при разделениях и слияниях,
аренду сегментов с ограждением и контрольные точки по каждому сегменту. Общие для фреймворка вещи -
подписчики, маршрутизация, кодеки, middleware - описаны в
[документации RustStream](https://powersemmi.github.io/ruststream/).

```toml
ruststream = { version = "0.7", features = ["macros", "json"] }
ruststream-kinesis = "0.7"
serde = { version = "1", features = ["derive"] }
```

## Совместимости {#capabilities}

Необязательные трейты-совместимости фреймворка и что с каждым из них делает этот крейт:

| Совместимость | Нативно | Примечания |
| --- | --- | --- |
| `Subscribe` | Да | Строковый литерал называет поток, поэтому `#[subscriber("orders")]` монтируется без дескриптора. См. [Подписки](#subscriptions). |
| `Seekable` + `Positioned` | Да | Обработчик читает, где лежит его запись, и перематывает подписку - и то и другое через контекст доставки. См. [Позиции](#positions). |
| `Partitioned` | Да | Доставленная запись сообщает свой ключ сегмента: по нему выбран её сегмент, по нему она и сохраняет порядок. См. [Публикация](#publishing). |
| `BatchSubscriber` | Да | Размер пакета, названный в точке монтирования, становится лимитом `GetRecords`, поэтому одно чтение забирает не больше одного пакета. См. [Пакеты](#batches). |
| `RequestReply` | Нет | В Kinesis нет ни адреса ответа, ни примитива корреляции; ответом стал бы второй поток, который крейту пришлось бы выдумать. |
| `TransactionalPublisher` | Нет | У сервиса нет транзакции: каждый элемент вызова `PutRecords` записывается или возвращает ошибку сам по себе. |
| `OwnedTransactions` | Нет | По той же причине: владеть нечем, транзакции нет. |
| `DescribeServer` | Да | Сгенерированный документ AsyncAPI называет хост и порт, к которым подключаются клиенты, под протоколом `kinesis`. См. [Сгенерированный документ](#the-generated-document). |

Подтверждение - не трейт-совместимость, поэтому в таблице его нет; что здесь делает `ack`, описано
в разделе [Аренда и контрольные точки](#leases-and-checkpoints).

`ruststream_kinesis::prelude` собирает в один glob прелюдию фреймворка и поверхность этого крейта:
`Seeker` для перемотки подписки, `Positioned` для чтения позиции доставленной записи и контексты
доставки `KinesisContext` и `KinesisBatchContext` вместе с ключами `Position` и `SeekHandle`,
которые их читают. Ключ сегмента записи читается через `IncomingMessage::partition_key`.

## Жизненный цикл {#the-lifecycle}

Каждый переход поглощает предыдущее состояние, поэтому каждое состояние - отдельный тип:

```text
KinesisBroker::new()      только конфигурация, синхронно, без ввода-вывода
  .connect()   ->  ConnectedKinesisBroker    живой клиент SDK; подписки и издатели
  .shutdown()  ->  ()                        читатели останавливаются, аренда истекает
```

`new` не делает ввода-вывода: регион и учётные данные разрешаются, когда рантайм подключает брокер.
`from_config(config)` принимает конфигурацию AWS, собранную отдельно, а `endpoint`, `region` и
`test_credentials` направляют брокер на локальный стенд.

`shutdown` поглощает подключённый брокер, поэтому подписка или публикация после него не
компилируется. Издатель, выданный раньше, переживает соединение и возвращает
`KinesisError::NotConnected`, а не пишет в поток, который сервис больше не читает.

## Подписки {#subscriptions}

`KinesisStream::new(name)` - дескриптор подписки: один поток, названный именем или ARN. Он стоит
прямо в декораторе `#[subscriber(..)]`:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_service.rs:handler"
```

Смонтируйте его на брокере:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_service.rs:app"
```

Сервис, собранный без фичи `macros`, передаёт тот же дескриптор конструктору `subscriber(source,
handler)`.

На дескрипторе задаётся и то, во что обходится чтение, а на Kinesis это решение, а не деталь:

| Настройка | По умолчанию | Смысл |
| --- | --- | --- |
| `poll_interval(d)` | 1 секунда | Пауза между чтениями простаивающего сегмента. Сервис разрешает пять чтений в секунду на сегмент, и короткая пауза тратит этот бюджет быстрее. |
| `create_if_missing(shards)` | выключено | Создаёт поток с таким числом сегментов, если его нет, и ждёт до минуты, пока он не станет рабочим. Предназначено для локальной разработки и тестов; поток в продакшене ведут как инфраструктуру. |

Обе настройки доступны и в точке монтирования - через трейт `KinesisSubscriberExt` из прелюдии;
пример в разделе [Пакеты](#batches) монтирует подписчик именно так. Они преобразуют дескриптор,
поэтому им нужен дескриптор для преобразования: `start_at(..)` заменяет его на позиционную обёртку
фреймворка, и они выстраиваются в цепочку до неё. Подписчик, у которого в атрибуте уже названа
стартовая позиция, задаёт их на дескрипторе - это те же два метода того же типа.

Неверный дескриптор отвергается до любого ввода-вывода.

Подписка перечисляет сегменты потока, перечисляет их заново, когда разделения и слияния меняют
набор, берёт аренду на каждый сегмент и держит по одному читателю на каждый сегмент, которым
владеет. Потомок разделения или слияния стартует только после того, как его родители прочитаны
целиком, и именно это сохраняет порядок по ключу при разделениях и слияниях.

Чтения идут через общую пропускную способность потока; enhanced fan-out не реализован. Запись,
агрегированная KPL, возвращается как ошибка, а не доходит до обработчика непрозрачным protobuf.

## Пакеты {#batches}

Обработчик, который принимает срез, читает пакет, а размер пакета называет его точка монтирования -
единственный параметр подписки, который фреймворк доводит до брокера. Здесь он становится лимитом
`GetRecords`, с которым запрашивает каждый читатель сегмента, поэтому одно чтение забирает не больше
одного пакета, и ни в одном пакете нет больше записей, чем названо:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_batches.rs:batches"
```

В пакете меньше записей, когда больше в сегментах ничего не было, а недобранный пакет доставляется
через 50 мс после первой своей записи.

В один пакет попадают записи всех сегментов, которыми владеет этот экземпляр. Каждая запись
подтверждается сама по себе, против отметки подтверждения своего сегмента, поэтому тело пакета,
которое возвращает исход на каждый элемент, ставит контрольную точку на каждую запись.

Размер - это ещё и решение о стоимости: маленький пакет означает маленькие чтения при тех же пяти
чтениях в секунду на сегмент. Этот бюджет тратит `poll_interval(..)`. Чтение, которое сервис
притормозил, - не сбой доставки: читатель ждёт один интервал и читает снова с того места, где
остановился, поэтому обработчик видит паузу, а не ошибку.

Тело пакетного обработчика читает `KinesisBatchContext`, а не `KinesisContext` - см.
[Позиции](#positions).

## Аренда и контрольные точки {#leases-and-checkpoints}

`ack` помечает запись обработанной. Контрольная точка покрывает все записи до неё, поэтому отметка
подтверждения сегмента продвигается и попадает в хранилище аренды только тогда, когда ни одна более
ранняя запись этого сегмента не осталась необработанной.

- `HandlerOutcome::ack()` помечает запись обработанной.
- `HandlerOutcome::retry()` оставляет её необработанной. Отметка останавливается на ней, поэтому
  сегмент проигрывается заново с этой записи, когда его аренду возьмут в следующий раз.
  Сегментированный лог перематывается; вернуть в очередь одну запись он не может.
- `HandlerOutcome::drop()` ставит контрольную точку за записью - так выводят из обращения ядовитую.

Доставка at-least-once: неподтверждённая запись держит отметку на месте, и всё, начиная с неё,
доставляется заново после перезапуска или передачи аренды.

Контрольные точки лежат в `LeaseStore`. `acquire` берёт сегмент для владельца и отбирает аренду,
срок которой истёк, `renew` продлевает её, `checkpoint` записывает продвижение, пока владелец ещё
держит аренду, `read` возвращает сохранённое состояние, а `release` отдаёт сегмент обратно, не
дожидаясь истечения срока. Неудачное продление означает, что сегмент забрал другой владелец, и такой
читатель останавливается сразу. Прочитанный целиком сегмент отмечается контрольной точкой
`SHARD_END` - это сигнал, что его потомки могут стартовать.

Хранилище по умолчанию - `MemoryLeaseStore`: внутри процесса, верное для одного экземпляра сервиса
и пустое после перезапуска.

### Повтор с задержкой {#retrying-after-a-delay}

В Kinesis нет таймера повторной доставки, поэтому обработчику, который вернул
`HandlerOutcome::retry_after(delay)`, помогает фреймворк: он публикует запись заново, когда
задержка вышла, и кладёт число повторов в заголовок. Политику, через которую уходит копия,
называет сама регистрация:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_retry.rs:retry"
```

Обработчик просит паузу и читает, сколько раз он уже просил:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_retry.rs:handler"
```

Копия уходит в тот поток, который читает подписка, и этот поток называет дескриптор. Регистрация
без `out_retry` задержку не держит: запись сразу проигрывается из сегмента заново.

Повтор - обычный слот `Out`, поэтому та же цепочка принимает `.codec(..)`, `.transform(..)` и
`partition_key(..)` этого крейта. Копия несёт собственные байты записи, поэтому кодек только
разрешает позицию и ничего не кодирует, а преобразование над копией всё равно отрабатывает.

Копия приходит в хвост потока, а не на место, которое занимала запись, и её ключ сегмента
выбирает сегмент, куда она ляжет. Поэтому отложенная запись теряет свой порядок относительно тех
записей, среди которых была опубликована. Там, где этот порядок важен, придержите сегмент через
`HandlerOutcome::retry()`: отметка останавливается на записи, и сегмент проигрывается с неё.

### Общие сегменты для нескольких экземпляров {#sharing-shards-between-instances}

Фича `dynamodb-lease` добавляет `DynamoLeaseStore`, и тогда несколько экземпляров сервиса делят
сегменты между собой. Таблице нужен строковый ключ раздела с именем `lease_key` и больше
ничего; тарификации on-demand достаточно. Каждая запись условная и увеличивает счётчик ограждения,
поэтому два экземпляра не могут держать один сегмент одновременно.

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_leases.rs:leases"
```

`owner_id` называет этот экземпляр в таблице; без него берётся значение, уникальное для процесса.

## Позиции {#positions}

`KinesisPosition` - весь словарь того, откуда читает подписка. По умолчанию каждый сегмент
продолжает со своей сохранённой контрольной точки, а сегмент без неё открывается в хвосте.

| Позиция | Область | Смысл |
| --- | --- | --- |
| `KinesisPosition::horizon()` | Весь поток | Горизонт обрезки: всё, что поток ещё хранит. |
| `KinesisPosition::latest()` | Весь поток | Хвост: только записи, опубликованные после перемотки. |
| `KinesisPosition::timestamp(millis)` | Весь поток | Каждый сегмент открывается на первой своей записи с этого момента, в миллисекундах от эпохи Unix. |
| `KinesisPosition::sequence(shard, seq)` | Один сегмент | Ровно одна запись. |

Позиция на весь поток действует и на сегменты, найденные позже, среди них на потомков разделения,
поэтому перемотка сохраняет свой смысл, когда поток меняет набор сегментов. Форма с областью в один
сегмент - это закреплённая позиция, которую фреймворк снимает с доставленной записи
(`Positioned::position`): перемотка на неё доставляет эту запись заново и не двигает остальные
сегменты. Ей нужен живой читатель этого сегмента в этом экземпляре, и она возвращает ошибку для
сегмента, которым этот экземпляр не владеет или который уже дочитал.

`start_at(..)` в декораторе открывает подписку на названной вами позиции, а не на сохранённой
контрольной точке. Работающая подписка перематывается из обработчика: этот брокер
кладёт в контекст доставки позицию записи и ручку перемотки подписки, а `Ctx<SeekHandle>`
связывает эту ручку с параметром обработчика:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_seek.rs:seek"
```

`Ctx<Position>` связывает так же собственную закреплённую позицию записи, а обработчик, которому
нужно и то и другое, называет типом контекста `KinesisContext` и читает ключи через
`ctx.context(..)`.

Пакетный обработчик получает `KinesisBatchContext`. В нём тот же `SeekHandle`, потому что перемотка
двигает всю подписку, и никакой позиции, потому что пакет охватывает много записей; тело, которое
реагирует на позицию, читает заголовки `kinesis-sequence-number` и `kinesis-shard-id` своих
элементов.

Перемотка сбрасывает учёт отметки у каждого сегмента, который она двигает, поэтому подтверждение
записи, доставленной до перемотки, не может утянуть курсор назад через только что занятую позицию.
Записи начиная с новой позиции доставляются заново, что at-least-once допускает. Сама совместимость
описана как [Перемотка](https://powersemmi.github.io/ruststream/latest/guides/subscribers/#seeking)
в документации фреймворка.

## Публикация {#publishing}

`KinesisPublish` - политика, которая конструирует `KinesisPublisher`, и рантайм инстанцирует его на
подключённом брокере при старте. Она же политика этого брокера по умолчанию, поэтому отвечающий
обработчик, смонтированный без явной политики, отвечает через неё.
`.out(Reply, Publish::default())` в точке монтирования называет её явно, и тот же вызов связывает
издателя внедрённого слота, когда вместо `Reply` стоит маркер этого слота.

Тело обработчика импортирует только фреймворк (`use ruststream::prelude::*`) и ограничивает
внедрённого издателя трейтом-совместимостью, поэтому оно никогда не узнаёт, на каком брокере
работает. Файл, который монтирует эти обработчики, импортирует
`use ruststream_kinesis::prelude::*`, где политика этого брокера носит единое для точки
монтирования имя `Publish`; `KinesisPublish` остаётся в корне крейта для файла, который монтирует
два брокера.

Билдер публикации - собственный билдер фреймворка: `message(..)` с объявленным типом, затем
`to(..)` с именем потока или ARN, `with_headers(..)`, `with_codec(..)` и `publish()`. Полезная
нагрузка, которую
сервис уже держит закодированной, объявляется newtype-обёрткой `#[derive(Outgoing, Serialized)]`:
кодек по ней не работает, а сгенерированный документ всё равно называет сообщение. См.
[руководство по публикации](https://powersemmi.github.io/ruststream/latest/guides/publishing/).

### Ключ сегмента {#the-partition-key}

Ключ сегмента выбирает сегмент, куда ляжет запись, а вместе с ним и порядок, который эта
запись сохраняет относительно соседей. Он принадлежит одной записи, а не издателю, поэтому это шаг
публикации, `partition_key(..)`, стоящий среди собственных шагов фреймворка:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_seek.rs:publish"
```

Шаг - это позиция на билдере, а не издатель, обёрнутый вокруг другого, поэтому запись по-прежнему
уходит через ту точку входа, которую назвала точка монтирования: её кодирует выбранный там кодек,
преобразования на ней по-прежнему работают, а тест по-прежнему относит публикацию к слоту этой
точки входа.

У ответа нет места вызова, куда поставить шаг: отвечающий обработчик возвращает значение, а
публикует его рантайм. Ключ ответа называют на политике, в точке монтирования, через трейт
`KinesisPublishSettings` из прелюдии:

```rust
--8<-- "crates/ruststream-kinesis/examples/kinesis_replies.rs:replies"
```

Один ключ - это один сегмент, а с ним и пропускная способность одного сегмента. Называйте ключ,
когда записи должны сохранять взаимный порядок, и не называйте в остальных случаях: если ключа нет
нигде, записи раскладывает по сегментам значение, уникальное для процесса.

Ключ могут назвать четыре места, и они разрешаются в одном порядке:

1. Шаг `partition_key(..)` этой публикации.
2. Заголовок `partition-key`, записанный вызовом вручную, - переносимое написание и то, что стоит в
   записи, пришедшей от другого брокера этого фреймворка.
3. Ключ, названный точкой монтирования на политике.
4. Значение, уникальное для процесса, которое раскладывает записи по сегментам: запись Kinesis не
   уходит без ключа.

Ключ передаётся в собственном поле записи для ключа сегмента, а заголовок - его переносимое имя на
обоих концах: издатель пишет разрешённый ключ в это поле и в конверт заголовок не кладёт, а доставка
сообщает ключ обратно в этом заголовке, где его находят `IncomingMessage::partition_key` и
диспетчеризация фреймворка по ключу. В доставке есть также `kinesis-sequence-number` и
`kinesis-shard-id` (`SEQUENCE_HEADER` и `SHARD_HEADER`).

Шаг - это настройка одного сообщения, а настройки одного сообщения - единственное, ради чего тело
обработчика произносит имя брокера. Тело, которое называет ключ, импортирует прелюдию этого крейта
и ограничивает свой слот типом опций:

```rust
--8<-- "crates/ruststream-kinesis/tests/harness_kinesis.rs:keyed_handler"
```

Эта сигнатура говорит, что тело написано под Kinesis. Тело, которое ключа не называет, оставляет
прелюдию фреймворка и обычное ограничение `Out<impl Publisher, _>` и переносится между брокерами
без изменений.

## Сгенерированный документ {#the-generated-document}

`DescribeServer` помещает брокер в секцию `servers` сгенерированного документа AsyncAPI, под
протоколом `kinesis`. Сообщает он координату: хост и порт, к которым подключается клиент.

- С `endpoint(..)` - хост и порт этого URL. Схема, имя пользователя и пароль отбрасываются:
  документ генерируют для публикации, и учётные данные не должны уходить вместе с ним.
- Иначе `kinesis.<region>.amazonaws.com`, если регион назван через `region(..)`.
- Иначе `kinesis.amazonaws.com`, потому что брокер, который берёт регион из окружения, к моменту
  сборки документа его ещё не взял.

## Конверт заголовков {#the-header-envelope}

В записи Kinesis есть только блоб данных и ключ сегмента, поэтому пользовательские
заголовки, кроме ключа сегмента, записываются в небольшой конверт вокруг полезной
нагрузки, и только тогда, когда такие заголовки есть:

- Запись, опубликованная без пользовательских заголовков, - это чистая полезная нагрузка, которую
  прочитает любой потребитель Kinesis, а запись, сделанная другим производителем, читается обратно
  как запись без заголовков.
- Иначе блоб - это четырёхбайтовая сигнатура `RSK1`, длина блока заголовков как `u32` с порядком
  байтов big-endian, сам блок заголовков и полезная нагрузка.

Ключ сегмента остаётся вне конверта: у записи для него есть собственное поле.

## Запуск на LocalStack {#running-against-localstack}

[LocalStack](https://localstack.cloud/) эмулирует Kinesis на машине разработчика. `just brokers-up`
поднимает контейнер, описанный в `docker-compose.test.yml`, а `just brokers-down` его удаляет.
Направляют брокер на него три настройки:

```text
KinesisBroker::new()
    .endpoint("http://localhost:4566")
    .test_credentials()
    .region("us-east-1")
```

Compose-файл закрепляет последний образ без токена, потому что более новые образы LocalStack
требуют токен авторизации, а pull request из форка не может прочитать его из секретов. Он же
выставляет `KINESIS_LATENCY=0`; иначе эмулятор добавляет 500 мс к каждому вызову.

## Тестирование {#testing}

Фича `testing` даёт `KinesisTestBroker` - внутрипроцессный транспорт, без сервера и без сети. У него
те же состояния, что и у настоящего брокера, и на нём работает обвязка `TestApp`. Ни одного
из этих имён в прелюдии нет, поэтому тест импортирует
`ruststream_kinesis::testing::KinesisTestBroker` и рядом `ruststream::testing::TestApp`. См.
[Юнит-тестирование сервиса через `TestApp`](https://powersemmi.github.io/ruststream/latest/guides/testing/#unit-testing-a-service-with-testapp).

Транспорт держит по хранимому логу на поток, потому что именно это свойство обработчик может
наблюдать без сервера. Подписка открывается в хвосте, там же, где открывается сегмент без
контрольной точки, а `start_at(..)` или `SeekHandle` из обработчика действительно перечитывают лог
с названной позиции. В доставке есть вся поверхность: `KinesisPosition`, заголовки
`kinesis-sequence-number` и `kinesis-shard-id`, ключ сегмента и `KinesisContext` или
`KinesisBatchContext`, через которые читаются ключи. Поэтому сервис монтируется без изменений:

```rust
--8<-- "crates/ruststream-kinesis/tests/harness_kinesis.rs:seek_handler"
```

```rust
--8<-- "crates/ruststream-kinesis/tests/harness_kinesis.rs:seek_test"
```

Монтирование с обеих сторон - собственное монтирование сервиса. `KinesisStream` открывает подписку
и здесь, с теми же настройками, что и в продакшене. `poll_interval` оценивает чтение, которого этот
транспорт никогда не делает, а `create_if_missing` нечего создавать, поэтому обе настройки
принимаются и игнорируются. Дескриптор, который сервис отверг бы, - пустое имя потока - не проходит
монтирование и здесь. `Publish` конструирует издателя этого транспорта, и он разрешает ключ
сегмента записи по тому же порядку из четырёх шагов, что и сервис, поэтому публикация с ключом
читается здесь так же, как будет читаться вживую. Она же политика подключённого транспорта по
умолчанию, поэтому ответ без собственного издателя уходит через неё. Ни тестового дескриптора, ни
тестовой политики нет.

Настройка одного сообщения записывается против того слота, через который ушла публикация, поэтому
обвязка проверяет её напрямую:
`tb.out::<Journal>().with_options(&KinesisPublishOptions { partition_key: Some(..) })` для вызова,
который назвал ключ, и `assert_options_default()` для того, который оставил настройки самой
политики нетронутыми.

Контрактные наборы фреймворка прогоняются на этом транспорте: маршрутизация
(`conformance::harness::run_suite`), последовательность переходов жизненного цикла
(`harness::lifecycle`), а также совместимости `Seekable` и пакетная
(`conformance::capabilities::seeking` и `batches`). Набор жизненного цикла доходит до издателя,
созданного до `shutdown`: после него издатель обязан вернуть ошибку, а не писать в закрытый
транспорт. Пакеты группирует клиентский адаптер фреймворка, поэтому пакетное монтирование здесь -
то же самое монтирование, что и против сервиса. Те же наборы прогоняются на LocalStack под
`KINESIS_TEST_ENDPOINT`.

Нет у этого транспорта того, чем владеет сервер: он маршрутизирует один сегмент
(`testing::IN_PROCESS_SHARD`), поэтому здесь нет ни аренды, ни долговечности контрольных точек, ни
пределов хранения, ни разделений и слияний, ни таймингов повторной доставки. Всё это покрывают живые
тесты за `KINESIS_TEST_ENDPOINT`:

```text
just test-brokers
```

Эта команда поднимает LocalStack и прогоняет собственные проверки крейта против него, однопоточно,
чтобы прогоны не видели потоки друг друга.
