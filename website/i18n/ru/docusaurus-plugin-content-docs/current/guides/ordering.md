# Сегменты, ключи сегмента и порядок

Это руководство выбирает сегмент каждой записи по её ключу сегмента, сохраняет порядок каждого ключа, пока обработчики работают параллельно, и сохраняет его, когда меняется число сегментов потока.

Пример - сервис заказов.
Он проводит каждый заказ в журнал покупателя по четыре заказа одновременно и подтверждает каждую проводку квитанцией.

## Как ключ выбирает сегмент {/* #how-a-key-picks-a-shard */}

У каждой записи Kinesis есть ключ сегмента.
Kinesis хеширует ключ алгоритмом MD5 и сохраняет запись в тот сегмент, в [диапазон хеш-ключей](https://docs.aws.amazon.com/streams/latest/dev/key-concepts.html) которого попадает хеш.
Kinesis сохраняет порядок записей внутри одного сегмента и не соблюдает порядка между сегментами.
Поэтому записи с одним ключом остаются по порядку, а записи с разными ключами распределяются по сегментам.

Пропускная способность одного ключа - пропускная способность одного сегмента: сегмент принимает до 1 МБ или 1000 записей в секунду.
Ключ, на который приходится большая часть трафика, делает свой сегмент пределом всего потока.

Магазин публикует каждый заказ с покупателем в качестве ключа сегмента, поэтому заказы одного покупателя лежат в одном сегменте в том порядке, в каком их оформили.
У потока `customer-orders` два сегмента, и подписка читает оба одновременно.

`workers(4, by_key)` запускает четыре партиции воркеров. Доставки с одним ключом выполняются друг за другом в одной партиции воркеров.
Ключ доставки - её ключ сегмента, который она содержит в [заголовке](../components/context/headers.md) `partition-key` ([`PARTITION_KEY_HEADER`](api:ruststream_kinesis::PARTITION_KEY_HEADER)).
Поэтому `post` обрабатывает четыре заказа одновременно и никогда не обрабатывает два заказа одного покупателя в одно и то же время.
В ручной форме ту же настройку задаёт [`workers_by_key`](api:ruststream::runtime::SubscriberSettings::workers_by_key).
Простой `workers(4)` выполняет четыре доставки одновременно без учёта ключей, и тогда два заказа одного покупателя могут завершиться в любом порядке.

## Как задать ключ записи {/* #naming-the-key-of-a-record */}

`post` записывает каждую проводку журнала с [`partition_key(..)`](../components/publishing/partition-key.md), шагом публикации.
Проводка попадает в сегмент своего покупателя, поэтому читатели журнала тоже видят каждого покупателя по порядку.
Этот шаг - настройка Kinesis, поэтому слот объявлен с ограничением `Publisher<Options = KinesisPublishOptions>`: только тогда публикация предлагает этот шаг.

У ответа нет вызова, к которому можно добавить шаг, поэтому точка монтирования задаёт его ключ в политике: [`.out_reply(Publish::default()).partition_key("receipts")`](../components/publishing/publish-settings.md).
Тогда все квитанции попадают в один сегмент, и читатели видят квитанции в одном порядке ценой пропускной способности этого сегмента.

Публикация выбирает [ключ](../components/publishing/keys.md) в следующем порядке:

1. Шаг `partition_key(..)` публикации.
2. Заголовок `partition-key`, который содержит публикация: записанный вручную или пришедший с записью из другого брокера RustStream.
3. Ключ, который точка монтирования задала в политике.
4. Новый ключ для каждой записи, который распределяет записи по сегментам.

Последний вариант не сохраняет порядка: две записи, опубликованные одна за другой, могут попасть в разные сегменты.
Тест примера задаёт ключ заголовком. Это переносимый способ: такой заголовок читает любой брокер RustStream.

## Разделение и слияние {/* #splits-and-merges */}

Разделение закрывает сегмент и открывает два дочерних, которые делят его диапазон хеш-ключей.
Слияние закрывает два соседних сегмента и открывает один дочерний.
Закрытые родительские сегменты хранят свои записи, пока не истечёт срок хранения.
Подписка заново перечисляет сегменты каждые десять секунд.
Она запускает дочерний сегмент, только когда каждый его родитель прочитан до конца, поэтому записи одного ключа сохраняют порядок при изменении.
Дочерний сегмент без контрольной точки открывается с самой старой записи, поэтому ничего, что записали в него до запуска читателя, не пропускается.
Страница [Сегменты, разделение и слияние](../architecture/kinesis/shards.md) показывает родительские и дочерние сегменты на схеме, а живые тесты крейта разделяют и сливают поток в `tests/shards_kinesis.rs`.

[Отложенный повтор](retries.md) публикует копию записи в конец потока, поэтому повторённая запись теряет своё место среди записей своего ключа.

## Тесты {/* #the-tests */}

Тесты в файле примера запускают приложение внутри процесса.
У каждого потока [Kinesis внутри процесса](../components/testing/index.md) один сегмент, поэтому тест, который читает заказы из двух сегментов, работает на стенде:

```bash
cargo test
KINESIS_TEST_ENDPOINT=http://localhost:4566 cargo test -- --test-threads=1
```
